## A 项目背景与动机（4 题）

### A1. 为什么做这个项目？

> **面试官想听**：动机是否具体。答"想练手 pandas"就废了，答"我有一个真实的决策难题"就对了。

这是我自己求职时的一个真实困惑。课本上学的 Hadoop、Hive、Spark 到底哪些是企业真在用的？学完能不能找到对口岗位？我得到的答案通常来自三种渠道：学长学姐的个人经验、招聘网站的零散岗位描述、培训机构的招生话术——前两者样本太小，后者立场不中立。

而招聘信息本身是一份**大样本、可量化、由企业用真实薪资预算投票产生**的需求数据。所以我把问题定义成：用招聘市场的数据，回答"专科应届生该学什么、投哪里、第一份工作从哪切入"。

**这个项目直接改变了我的求职计划**——原本准备毕业就投大数据开发工程师，现在改成先投数据运维、ETL，两年后再转。

---

### A2. 为什么选这个题目，而不是电商销售分析、豆瓣电影分析？

> **面试官想听**：能不能说出选题的"必要性"，而不是"因为我只找到这个数据"。

三个原因。

第一，**决策相关性**。电商销售分析我也能做，但那份结论对我、对面试官都没有行动价值；招聘数据的结论直接对应"我下个月该学什么"。

第二，**数据本身有业务逻辑**。每一行招聘信息背后是一次真实的招聘行为，薪资是企业真金白银的预算，岗位描述是技术栈的真实要求，不是人为构造的评分数据。

第三，**它逼着我处理脏数据**。薪资是字符串、职位描述是富文本、还有大量重复采集——这些正是数据处理岗每天要面对的问题，比干净的数据集更能体现能力。

---

### A3. 这个项目的业务价值是什么？谁来用？

> **面试官想听**：有没有"用户"意识。

直接用户是我自己——它输出了一份可执行的投递清单：3 个切入岗位、3 座主战场城市、6 个技能的学习顺序。

扩展到同类人群也成立，比如专业相同但还没做调研的同学。如果做成可交互工具（选城市 + 学历 + 经验，输出匹配方向和技能清单），使用范围会更大——这也是我后续想做的优化方向之一。

对招聘方的价值是反过来的：它能看出**一个候选人是否理解"结论的适用条件"**。同样的技术栈，有人做完只会说"大数据薪资高"，有人能说清"这个 22.5K 是在什么口径下算出来的、在什么条件下不成立"。这个差别就是初级和中级分析师的分界线。

---

### A4. 这个项目你做了多久？难点在哪？

> **面试官想听**：能不能分清"工作量"和"难点"。说不清难点的人通常是照着教程做的。

从拿到数据到出报告大概两周，其中写代码只占三分之一，**大部分时间花在判断"这个数据能不能用"上**。

最难的不是技术，是三个判断：

1. **数据到底是怎么采的**——发现它是按类别封顶采样，这一步推翻了我原来的所有占比结论；
2. **去重删掉 31% 到底对不对**——必须找到证据才敢删；
3. **Spark 那 35% 的溢价是真的吗**——必须做分层控制才能确认它是伪相关。

技术上最难的一处反而很具体：技能抽取用 `if "SQL" in text` 会把 **MySQL 误判成 SQL**，必须用非字母边界正则 `(?<![A-Za-z])SQL(?![A-Za-z])`。不加这个，SQL 的命中率会被严重高估，整条结论失真。

## B 数据与口径（6 题）

### B1. 数据从哪来的？为什么不用爬虫？

> **面试官想听**：合规意识和可复现意识。这题答"爬虫被反爬了所以用公开数据"是减分的。

用的是和鲸社区公开的拉勾招聘数据集，原始采集自 lagou.com 的公开职位列表页，21,320 条 × 21 列。

不自己爬，是三个权衡：

1. **合规**。招聘网站的用户协议通常禁止未授权自动化采集，职位描述里还可能含企业联系方式等非公开信息。个人项目用公开数据集可以规避这个风险。
2. **可复现**。作品集项目的价值之一是可被检验——面试官可以下载同一份数据、跑同一套脚本、得到同一个结论。
3. **表述准确**。用公开数据就如实说用公开数据，不能暗示"我爬了两万条"。后者一被追问反爬策略、IP 池、请求频率就会露馅，反而扣分。

---

### B2. 1.4 万条数据，能代表整个市场吗？

> **面试官想听**：你会不会主动给自己划边界。这题**必须**先答"代表不了"，再答"但够用"。

**代表不了市场规模，这一点我在报告里明确写了。**

它有两个偏差：一是单一平台（只有拉勾，偏互联网和科技行业）；二是**按类别封顶采样**——70 个岗位类别里 33% 的记录数集中在 440 到 450 之间，而现实中 Java 的岗位量是 Perl 的几十倍，这份数据里两者几乎一样多。所以任何"某类岗位占市场百分之几"的结论都不成立，我全文只用"**样本内占比**"这个口径。

但它对我要回答的问题够用：我要比较的是**类别内部**的技能要求和薪资结构，不做跨类别的规模排名。大数据方向有 582 条，做组内比较样本量是充足的。

**边界划清了，结论才站得住**——这比硬说"数据很有代表性"要安全。

---

### B3. 21 个字段你都用了吗？你构造了哪些衍生字段？

> **面试官想听**：理解"原始字段 ≠ 分析变量"。

21 个字段分四组：标识类（positionId、companyId、createTime）、岗位描述类（positionName、category、positionType）、薪资与要求类（salary、city、education、workYear）、企业与文本类（companySize、industryField、financeStage、positionDetail）。

真正参与分析的核心是 `salary`、`education`、`workYear`、`city` 和 `positionDetail` 五个。原始字段直接能用的很少，我构造了四类衍生字段：

1. **岗位方向**——基于 positionName 和 category 做关键词映射，归成 8 个方向，再用 `is_bigdata` 标记大数据岗（582 条）；
2. **城市等级**——一线 / 新一线 / 二线 / 其他，用来控制混淆变量；
3. **技能标签**——18 个技能从 positionDetail 里抽出来，共 20 个布尔列；
4. **薪资质量标记**——异常类型 flag 和低薪标记，供敏感性检验用。

最终从 21 列扩到 59 列。

---

### B4. 薪资你是怎么算的？为什么用中位数不用均值？

> **面试官想听**：知不知道分布形态对统计量的影响。这是**送分题，答错很致命**。

原始 `salary` 是"20k-35k"、「15k-25k·13薪」这种字符串，先用正则拆出上下限和薪资月数，再取上下限的平均值作为月薪口径。

**用中位数不用均值，是因为分布右偏**：全体均值 21.3K、中位数 18.5K，均值被少数高薪岗拉高了 2.8K。分位数看得更清楚——P10 是 8.5K，P90 是 37.5K，相差 4.4 倍。

技术岗薪资是典型的长尾分布，如果报均值，一个 100K 的架构师岗能顶掉好几个普通岗。**中位数才反映"中间那个人拿多少"**，也更接近求职者的真实体感。所以全文所有分组比较一律用中位数。

> **追问陷阱**："那均值完全没用吗？"
> 有用——**均值和中位数的差距本身就是信息**。差得越大说明分布越右偏、高薪岗越集中。我在 EDA 里把这个差距当成分布形态的指标在用。

---

### B5. 时间跨度两年，为什么不做趋势分析？

> **面试官想听**：知不知道数据的时序质量。乱答"因为数据不够"是不合格的。

两个原因。

第一，**样本在时间上不是均匀分布的**。这份数据不是按时间连续采集的，各月份的记录数差异很大，做月度趋势会把"采集量"误当成"需求变化"。

第二，**跨度不足以支撑趋势结论**。2022.08 到 2024.01 只有 17 个月，中间还跨了行业招聘周期的波动，用这么短的窗口讲"大数据需求在上升还是下降"，很容易得出错误结论。

所以我把这个项目定位成**横截面分析**——只看"在这个窗口内，市场要求什么"，不做时间维度推断。这也是报告里写明的局限之一。

---

### B6. 如果给你更多数据，你最想补什么？

> **面试官想听**：你知不知道自己缺什么。

按优先级三个：

1. **多平台**（BOSS 直聘、猎聘）。如果两个平台的技能要求排序一致，结论可信度会显著提升；如果不一致，那本身就是有价值的发现——说明不同行业的用人偏好不同。
2. **更多维度**。现在的数据没有"是否接受专升本""是否提供培训""团队规模"这些字段，而这些恰恰影响专科生的实际选择。
3. **时序数据**。如果是连续采集的，可以做趋势和生存分析，回答"从 1–3 年跨到 3–5 年需要多久、薪资涨多少"这类职业路径问题。

## C 清洗与数据质量（7 题）

> 这一组是**数据开发岗的核心考察区**，建议每题都能讲到具体数字。

### C1. 清洗做了哪几步？删掉了多少数据？

8 个步骤，从 21,320 条降到 14,725 条：

| 步骤 | 变动 |
| :--- | ---: |
| 剔除无用列（21 → 19 列） | 0 |
| HTML 标签清洗（99.6% 的职位描述含标签） | 0 |
| 薪资结构化 + 异常剔除 | −15 |
| **按 positionId 去重** | **−6,580（31%）** |
| 全字段去重 | 0 |
| 剔除关键字段缺失 | 0 |
| 描述字段填充 | 0 |
| 类型转换 + 衍生字段 | 0（列数 22 → 59） |

**最大的变动就是去重那一步，删了 31%**，剩下基本都是零变动——说明这份数据在关键字段上完整性其实不错，脏的地方集中在"重复"和"富文本"上。

---

### C2. 去重删了 31%，你怎么证明删对了？

> **面试官想听**：这题是**分水岭**。答"drop_duplicates 一下就好了"= 没见过真数据；答"我先验证了两条证据"= 有数据敏感度。

31% 这个比例本来就反常，所以我不敢直接删，先做了两个检验：

1. **跨城市重复检验**——3,568 个重复的 positionId 组里，同一个 ID 出现在不同城市的组数是 **0**。说明不是不同城市发布了同名岗位，而是同一岗位被重复采集了。
2. **组内薪资一致性**——重复组内部各条的薪资 **100% 相同**。

两条证据都指向同一结论：**这是同一岗位的多次抓取，不是真实的多条招聘需求**。确认之后才删，保留 `createTime` 最新的一条。

反过来想：如果不做这个验证就删 31%，那是经不起追问的；如果不去重，所有"岗位数量"类统计都会失真，尤其是城市排名——同一岗位被抓了三次，那个城市的岗位数就虚高三位。

---

### C3. 异常值你是怎么处理的？为什么不用 IQR？

> **面试官想听**：知不知道机械方法和业务方法的分界。这是**最容易被问倒**的一题。

我**没有**用 IQR 或 3σ，改成了按业务含义分类处理：

| 类型 | 判定规则 | 业务含义 | 处理 |
| :--- | :--- | :--- | :--- |
| 无法解析 | 正则不匹配 | 字段格式异常 | 剔除 |
| 上限小于下限 | max 小于 min | 明显录入错误 | 剔除 |
| 疑似年薪误填 | min ≥ 100 | 月薪不可能达十万以上 | 剔除 |
| 区间跨度过大 | max ÷ min 超过 8 倍 | 上下限可能单位不一致 | 保留但打标 |
| 低薪可疑岗 | avg 不足 3K | 疑似虚假招聘或实习岗混杂 | 保留但打标 |

理由是：**机械规则分不清"错误"和"罕见但真实"**。IQR 规则会把一批真实的 40K 以上高薪岗当成异常值干掉，而技术岗薪资本身就是右偏长尾——高薪不是异常，是常态的一部分。

真正错的只有那两类（上限小于下限、月薪十万以上），它们占总数的 0.07%，一共剔了 15 条。

至于"跨度过大"和"低薪"，它们可能真实存在，所以只打标不删，留着后面做敏感性检验。

---

### C4. 你说做了敏感性检验，具体怎么做？

> **面试官想听**：这题是回答"删异常值会不会影响结果"的**标准解法**。

做两套口径对比：**剔除异常版** vs **把打标的异常记录加回去**，重新算一遍核心指标。

结果：

| 指标 | 剔除异常 | 加回异常 | 差异 |
| :--- | ---: | ---: | ---: |
| 全体技术岗中位数 | 18.5 K | 18.5 K | **0** |
| 大数据岗中位数 | 22.5 K | 22.5 K | **0** |
| 全体均值 | 21.32 K | 21.29 K | 0.03 K |

中位数**完全一致**，均值只有 0.03K 的波动，说明异常记录占比不到 1%，结论不受影响。

顺手还用同样的方法验了城市排名的稳定性——两套口径下 Top8 城市的顺序完全一致。

**这个方法的要点是：不要口头保证"影响不大"，而是做两套口径跑一遍，用数据回答。**

---

### C5. HTML 标签清洗是怎么回事？为什么说它"不做就会全错"？

99.6% 的职位描述是富文本，含 `<br />`、`&nbsp;`、`<p>` 这类标签。

它虽然不改变记录数，但**决定了后续技能抽取的准确率**。比如换行符和 HTML 实体会导致跨词匹配失败——"熟悉<br/>Hive" 里搜 "Hive" 还能命中，但如果是 `Hive&nbsp;Spark` 这种，简单的字符串查找就会漏。

处理方式是统一用正则剥标签、还原实体字符、把连续空白压缩成单个空格。`positionAdvantage`（福利标签）做同样处理。

这一步是典型的"做了看不出来、不做全盘崩"——后面 20 张分析表全部依赖职位描述文本，文本脏了，技能命中率就全是错的。

---

### C6. 技能标签是怎么抽的？怎么保证准确？

> **面试官想听**：细节。这题有个很具体的技术点，答出来会明显加分。

词典 18 个技能（Hadoop、Hive、Spark、Flink、HBase、Kafka、Yarn、MapReduce、Zookeeper、ClickHouse、SQL、MySQL、Oracle、Redis、Java、Python、Scala、Shell、Linux、ETL、数据仓库），从清洗后的职位描述里做匹配。

**最关键的一个细节是：不能用简单的子串匹配。**

朴素做法 `if "SQL" in text` 会把 **MySQL 误判成 SQL**——MySQL 的命中率是 12.6%，这部分会被错误地全部计入 SQL。修正后 SQL 在大数据岗是 34.1%、全体岗 9.1%、差值 +25.0 pp；不修正的话 SQL 会被高估到接近 MySQL 的水平，差值严重失真，直接影响"该学什么"的结论。

正确做法是对英文字符技能用**非字母边界正则**：

```python
def has_skill(text, skill):
    if skill.isascii():
        # 前后不能紧跟其他字母，避免 SQL 命中 MySQL、Hive 命中 archive
        return re.search(r"(?<![A-Za-z])" + re.escape(skill) + r"(?![A-Za-z])", text, re.I) is not None
    return skill in text  # 中文技能词直接子串匹配
```

另外技能列最后存成 `int8` 的 0/1 而不是布尔类型——因为 CSV 回读之后布尔列会变成字符串，后续 `sum()` 直接报类型错。这是踩过坑之后的处理。

### C7. 缺失值你怎么处理的？

> **面试官想听**：是否分级处理，而不是一刀切。

按"是否影响核心结论"分三级：

| 级别 | 字段 | 处理 | 理由 |
| :--- | :--- | :--- | :--- |
| 关键字段 | salary、city、education、workYear、positionName | 有缺失即剔除 | 缺了就无法参与任何分组分析 |
| 描述字段 | companySize、financeStage、industryField | 填充"未知" | 仅作辅助维度，填充后能保住样本 |
| 文本字段 | positionDetail | 保留空值 | 技能抽取时按"未命中"处理即可 |

实际执行后关键字段缺失是 0 条。182 条企业规模为"未知"的记录被保留成单独一组，**它的薪资中位数是 33.2K，明显偏高**——大概率是大厂没标规模。这一组在解读规模与薪资关系时是要单独说明的干扰项，不能混进趋势里。

## D 分析方法（6 题）

### D1. 你是怎么得出"技能不构成溢价"这个结论的？

> **面试官想听**：**这是整个项目最核心的一题**。答好了直接证明你有中级分析师的思维。

分两步，第二步是关键。

**第一步，全样本算原始溢价**：具备某技能的岗位薪资中位数，减去不具备的。结果看起来很清晰——要求 Spark 的岗位薪资高 6.5K、也就是 35.1%；MapReduce 更高，+11.5K、62.2%。

但这是**原始相关关系，不是因果**。高薪岗要求 Spark，不代表学 Spark 就能涨薪，也可能只是"要求 Spark 的岗位本身层级更高"。

**第二步，控住混淆变量再算一次**：把城市等级固定在一线/新一线、经验固定在 1–5 年、只在大数据岗内部比较（n=333）。

结果反转了：Spark 从 **+6.5K（+35.1%）变成 −2.5K（−11.1%）**，Hive、HBase 也是 −2.5K。只有 Kafka（+1.8K）和 ClickHouse（+1.5K）还保持正溢价。

**这说明什么**：那 35% 的溢价来源不是"Spark 稀缺"，而是"要求 Spark 的岗位恰好是数据开发岗，而数据开发岗本身薪资更高"。在数据开发岗内部，Spark 是标配——会它不加分，不会它进不去。

**这个方法论的要点**：相关不等于因果，而排除混淆变量的方法不是口头声明，是**分层**——把可能的混杂因素固定住，再看差异是否仍然存在。

---

### D2. 为什么用箱线图，不用柱状图？

薪资是右偏分布（均值 21.3K、中位数 18.5K），柱状图只能画均值，会被少数高薪岗拉偏。

箱线图能同时展示**中位数、中间 50% 的区间（箱体）、整体跨度（须线）和离群值**，信息密度更高，也更接近求职者的真实体感。

而且箱体高度本身就有业务含义：大数据岗中间 50% 集中在 15.6K–30.0K，箱体相对紧凑，说明这个方向薪资更集中、更可预期；后端开发的箱体从 12.5K 拉到 26.0K，离散度更大——同样的岗位在不同公司待遇差别悬殊。

> **追问陷阱**："那你图上那个红色菱形是什么？"
> 是均值。我特意把均值和箱体中位线都画出来，就是为了让人一眼看到均值高于中位数——右偏是看得见的。

---

### D3. 为什么用条形图对比技能，不用词云？

词云只能看相对频率，**看不出一个技能是不是大数据岗专属的**。

判断学习优先级需要的是**区分度**，不是**出现频次**。所以这张图做了对照组：用大数据岗的命中率减去全体技术岗的命中率，差值才是真正的区分指标。

效果很明显：Hive、Spark、数据仓库、Hadoop 的差值都在 +35 pp 以上，是这条赛道的入场券；而 **Linux 在大数据岗是 15.8%、全体岗是 15.9%，差值 −0.1 pp**——它不是加分项，是及格线，会了不加分，不会直接被筛掉。

如果用词云，Linux 和 MySQL 这类通用技能会因为出现频繁而显得很重要，把学习重点带偏。

---

### D4. 城市分析为什么先过滤样本量？

这是城市分析里最常见的坑。

不过滤的话，三亚、鸡西这种只有一两条记录的城市，会因为个别高薪岗直接冲到薪资榜首（实测三亚 45K、鸡西 30K），得出完全错误的排名。

所以我设了门槛：**只保留样本量 ≥ 50 的城市**。过滤后 Top8 变成北京 27.5K、上海 22.5K、深圳 21.0K、杭州 20.0K……顺序稳定，两套口径下也一致。

这个处理背后是个通用原则：**小样本的极值不可信**。凡是做分组统计，先看每组有多少条，不够就先合并或剔除。

> **加分补充**：同样的坑我在交叉分析里也处理了——经验 × 学历的交叉表，单元格样本量不足 10 条的直接置空不报数，而不是让它显示一个漂亮但无意义的数字。

---

### D5. 你的分析分了四层，为什么这么设计？

因为**只做前两层，得到的是一堆好看的图表；加上后两层，才能知道结论的边界在哪**。

| 层次 | 内容 | 回答什么 |
| :--- | :--- | :--- |
| A 样本概况 | 描述统计、分布结构 | 这份数据长什么样 |
| B 分组对比 | 方向、技能、城市、学历四个维度 | 差异在哪里 |
| C 交叉分析 | 经验×学历、城市×学历、规模×薪资 | 差异是不是别的因素造成的 |
| D 稳健性检验 | 敏感性检验、样本结构检验 | 结论能不能站得住 |

C 层和 D 层是这个项目的骨架。比如"一线城市大专岗 13.5K vs 二线城市本科岗 13.0K"这个对比就在 C 层——它说明在一线以专科身份拿到的薪资，和二线以本科身份拿到的基本持平，但一线的大数据岗数量是新一线的 3–5 倍，机会密度完全不同。

---

### D6. 漏斗图那 5 个岗位，口径是不是有问题？

> **面试官想听**：这题是在考你会不会**自己审自己的口径**。答"应该没问题"就完了。

口径我改过一次，而且严格口径下其实是 **0 个**，两个数我都写进报告了。

初版只把"在校/应届"算作应届可投，算出来末级是 0 个——因为大数据岗几乎没有明确写招应届的。但这明显低估了机会量：**"经验不限"的岗位应届生同样可以投**。

所以最终口径改成宽口径：经验要求是"经验不限"或"在校/应届"都算。这样末级是 5 个。

两个数并存，含义不同：
- **宽口径 5 个**——理论上能投；
- **严格口径 0 个**——明确写招应届的，一个都没有。

还有个对照数据很说明问题：如果把学历限制放开，只看面向应届的大数据岗，有 **94 个**；而专科可投的大数据岗（不限经验）有 **39 个**。两个数一起看，说明**卡住的主要是学历，不是经验**。

## E 结论与业务理解（4 题）

### E1. 你的四条结论，哪一条最反直觉？

第四条——**别用"我会 Spark"去谈薪**。

网上普遍的说法是"学 Spark 能涨薪 35%"，我做完分层控制发现是 −11%。这个反转的实际含义是：**简历上写技能名词没用，写能力和结果才有用**。

"熟悉 Spark"改成"用 Spark 处理过 X 亿条日志，把报表产出时间从 4 小时压到 25 分钟"——企业买的是解决问题的能力，不是技能名词。

这一条直接改变了我写简历的方式。

---

### E2. 如果让你给公司提一个建议，你会提什么？

> **面试官想听**：能不能从"分析学生就业"跳到"分析企业招聘"。**这题答好了能反客为主。**

基于这个数据，我会提一个关于**招聘 JD 写法**的建议。

数据显示，大数据岗要求 Spark 40.4%、Hive 40.0%，但这两个技能的候选池其实高度重叠——Hive + Spark 同时出现于 30.2% 的岗位。也就是说很多 JD 在重复描述同一类能力。

另外，**JD 里的技能要求与薪资并不对应**——我们做了分层控制后发现，技能本身几乎不产生溢价，真正拉开差距的是岗位方向和层级。这意味着企业如果真想要某个稀缺技能的人，光在 JD 里堆技能名词是招不到的，得在薪资带宽上做区分。

当然这只是从招聘广告侧观察到的，实际招聘效果还需要内部数据验证。

### E3. 漏斗只剩 5 个岗位，是不是说明大数据方向不该选？

**恰恰相反，这张图最大的价值是精确定位了卡点在哪。**

看每级之间掉多少：学历这道筛掉 80.1%（这是最大的门槛）；方向这道从 2,865 掉到 39；经验这道从 39 掉到 5。

再结合两个对照数据——放开学历后面向应届的大数据岗有 94 个，说明卡住的主要是学历不是经验。

所以结论不是"不该选"，而是"**入口窄但出口宽**"：行业入口是窄的，就从侧门进。先做技能栈相邻的岗位（数据运维 884 个专科可投岗、后端开发 861 个、测试 349 个），积累 1–2 年真实数据处理经验再转岗，比现在硬投校招大数据岗成功率高得多。

**如果我这个分析只做出"大数据薪资很高"这一层结论，反而会误导自己去硬投。**

### E4. 专科生做这个项目有什么意义？

> **面试官想听**：会不会自卑或者过度包装。要答得不卑不亢。

意义在于**它把一个模糊的焦虑变成了一个可量化的问题**。

"专科生能不能进大数据"这个问题，在网上只能得到两种答案：一种是培训机构说"完全可以，学完就月薪 20K"，一种是论坛说"没本科别想了"。两个都没有依据。

我用数据把它拆成了三个可验证的子问题：学历门槛有多高（大数据岗本科占 88.2%、大专只占 5.0%）、方向是否值得（薪资中位数高 3.5K）、切入路径是什么（运维/ETL/后端）。

数据给的答案不好听——专科加应届只剩 5 个岗位——**但它是可行动的**：正因为入口窄，我才知道要绕路，而不是在毕业季投三个月简历然后怀疑自己。

**能接受一个不好听但准确的结论，我觉得这比结论本身更像"数据分析"。**

## F 工程与实现（2 题）

### F1. 代码怎么组织的？能跑通吗？

4 个独立模块，约 1,100 行，按链路顺序执行：

| 文件 | 职责 | 输出 |
| :--- | :--- | :--- |
| `01_data_cleaning.py` | 8 步清洗 | `clean_jobs.csv`（14,725 × 59）+ `cleaning_log.txt` |
| `02_eda_analysis.py` | 4 层 / 20 张分析表 | `eda_results.txt` |
| `03_charts_data.py` | 计算 4 张图的精确坐标 | `charts_data.json` |
| `03_visualization.py` | matplotlib 出图 | 4 张 PNG |

两个设计上的考虑：

1. **中间产物落盘**。清洗结果存成 CSV，EDA 直接读它——这样调分析逻辑不用重跑清洗，而且任何人可以拿 `clean_jobs.csv` 复核我的结论。
2. **图表数据与绘图分离**。`03_charts_data.py` 只算坐标（箱线图的 q1/中位数/q3/须线、气泡的 xy 和半径），`03_visualization.py` 只负责画。好处是同一份坐标既能给 matplotlib 用，也能给网页的原生 SVG 用——我最后就是这么做的，网页版图表和 PNG 版完全同源。

报告里每一个数字都可以在 `eda_results.txt` 里逐条核对。

> **追问**："1.4 万条用 pandas 跑得动吗？"
> 完全跑得动，全流程不到 10 秒。这个量级远没到需要 Spark 的程度——**用简单的工具解决问题，比为了用大数据框架而用大数据框架更专业**。如果数据量到千万级，才需要考虑上分布式。

---

### F2. 图是怎么画的？中文乱码怎么解决的？

两套实现：

**matplotlib 版**（`03_visualization.py`）——中文字体要显式设置，否则全是方块：

```python
plt.rcParams["font.sans-serif"] = ["Microsoft YaHei", "SimHei"]
plt.rcParams["axes.unicode_minus"] = False  # 负号显示，不设会变成方块
```

还有一个很隐蔽的坑：**箱线图必须用 `ax.bxp()` 传预计算的统计量**，不能直接 `ax.boxplot([[q1, med, q3, ...]])`——后者会把那 5 个数当成原始数据重新算一遍四分位，画出来的箱体和真实数据完全对不上。

**网页版**——用的是原生 SVG 手绘，不依赖任何 CDN。好处是离线可用、可以直接嵌进 GitHub Pages、加载快、还能做交互（悬停显示数值）。PNG 版是用无头浏览器渲染 SVG 页面导出的，所以两版图形完全一致。

## G 反思与压力题（5 题）

### G1. 这个项目最大的问题是什么？

> **面试官想听**：这题**必须**给出一个真实的、有分量的缺陷，不能答"数据量不够"这种表面问题。

最大的问题是**数据本身是被采样过的，我却差点没发现**。

如果能重做，我会在写第一行分析代码之前，先做一次完整的**样本结构检验**——统计每个类别的记录数分布、检查是否有截断、检查时间分布是否均匀。

**教训是：分析的第一步不是 `df.describe()`，而是先问"这份数据是怎么来的"。**

### G3. 你觉得这个项目能打几分（满分 10 分）？

**7 分。**

### G4. 你说会先做数据运维再转数据开发，是不是因为大数据岗你投不进去？

> **面试官想听**：压力测试。答"不是"就是嘴硬，答"是"就是没主见。**要答成"数据支持的战略选择"。**

是，短期确实投不进去——数据上很清楚：577 个大数据岗里专科加应届只剩 5 个，严格口径 0 个。

但这不是退而求其次，是**数据算出来的最优路径**。三个理由：

1. **技能栈重叠度高**。大数据岗要求 Java 36.6%、Python 35.9%、ETL 23.4%，这些正是后端和数据运维岗的日常，转岗时不需要从零开始。
2. **入口宽得多**。运维方向 884 个专科可投岗，后端 861 个，测试 349 个——比死磕 5 个岗位的期望值高得多。
3. **招聘方也认这条路**。大数据岗 88.2% 要求本科，但同时有 39 个岗位接受专科、94 个岗位面向应届——真正卡我的是"专科 + 应届"这个组合，不是"专科"或"应届"单一条件。用两年时间换掉"应届"这个标签，可投的岗位量会明显变化。

所以我的规划是：第一份工作先进行业、进数据处理链路，两年后带着真实的数据量和链路经验再转。
